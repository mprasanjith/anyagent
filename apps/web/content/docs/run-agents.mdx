This page covers the core workflow: find the agents installed on the end user’s machine, pick one, and run a prompt with the options your feature needs. Every snippet that runs a prompt assumes at least one [supported agent](/docs/adapters) is installed and signed in.

## Find what is installed

Call `detect()` to scan the end user’s `PATH` for every supported agent. It returns one `DetectResult` per installed agent, and an empty array when none are found:

```ts
import { detect } from "anyagent";

const installed = await detect();
for (const found of installed) {
  console.log(`${found.name} ${found.version ?? "unknown"} at ${found.path}`);
}
```

On a machine with Claude Code and Codex installed, this prints:

```txt
Claude Code 2.0.31 at /home/sam/.local/bin/claude
Codex 0.48.0 at /usr/local/bin/codex
```

Each result carries the agent’s `id`, `name`, `path`, reported `version`, its capabilities, and the adapter that drives it; [`DetectResult`](/docs/api#detectresult) lists the fields. The order of results carries no preference, so which agent to run is your product decision.

## Choose which agent to run

Before you run anything, name the agent and the task you are about to drive: the prompt runs under the end user’s login and bills their subscription, so nothing should run by surprise. When several agents are installed, ask rather than pick:

```ts
import { create, detect } from "anyagent";
import { createInterface } from "node:readline/promises";

const installed = await detect();
const [first] = installed;
if (!first) {
  throw new Error("No supported coding agent found.");
}

const rl = createInterface({ input: process.stdin, output: process.stdout });
installed.forEach((a, i) => console.log(`${i + 1}. ${a.name}`));
const answer = await rl.question("Which agent should acme init use? ");
rl.close();

const agent = create(installed[Number(answer) - 1] ?? first);
```

`create()` accepts a `DetectResult` directly and returns a runnable `Agent`.

## Handle a machine with no agent

An empty array means no supported agent is installed. When the agent adds an optional feature, say so and continue with your manual path. When it is required, name the CLIs you support from the [supported agents](/docs/adapters) and how to install one:

```ts
import { detect } from "anyagent";

const installed = await detect();
if (installed.length === 0) {
  console.error(
    "acme init needs a coding agent. Install a supported CLI, sign in, and rerun."
  );
  process.exit(1);
}
```

## Target one specific agent

When your tool supports exactly one agent, skip detection and import its adapter from its own subpath, so your bundle pulls in only the adapter you use:

```ts
import { create } from "anyagent";
import { claudeCode } from "anyagent/claude-code";

const agent = create(claudeCode());
```

Creating an agent from an adapter never checks that the CLI is installed, so a missing binary surfaces as an [`Invocation` error](/docs/errors#invocation) on the first run. An agent created this way is also typed to its adapter’s exact capabilities, so an option the CLI does not support fails to compile instead of at runtime.

## Check credentials before you run

An installed CLI is not necessarily a signed-in one. `agent.authStatus()` answers whether credentials are configured, without ever making a paid model call:

```ts
import { create } from "anyagent";
import { claudeCode } from "anyagent/claude-code";

const agent = create(claudeCode());
const auth = await agent.authStatus();

if (auth.state === "unauthenticated") {
  console.error("Claude Code is installed but not signed in. Run: claude login");
  process.exit(1);
}
```

How much to trust the answer depends on `agent.capabilities.authStatus`: `"native"` means the CLI answered itself, while `"probed"` means AnyAgent read the CLI’s credential files and environment variables, a hint rather than a guarantee. Treat `"unknown"` as “worth trying a run”; it comes back when, for example, the key lives in an OS keyring the probe cannot read.

`agent.models()` answers the second discovery question: which models this agent accepts, each [`ModelInfo.id`](/docs/api#modelinfo) valid verbatim as the `model` option on the same agent. Both methods throw [`UnsupportedCapability`](/docs/errors#unsupportedcapability) on an agent whose capabilities declare them `false`, so guard with `agent.capabilities.authStatus` and `.modelListing` when the agent is not known in advance; the [support matrix](/docs/adapters) shows who answers what.

## Run a prompt and read the result

`agent.run(prompt, opts)` sends one prompt and resolves with a [`RunResult`](/docs/api#runresult) when the agent finishes. The run is unattended: the agent edits files and runs commands with the most autonomy its CLI offers, and nothing can approve or reject an action mid-run. So write a scoped prompt: name the files the agent should touch, state the goal, and forbid what it must leave alone, so the end user reviews a small diff instead of a surprise:

```ts
import { create } from "anyagent";
import { claudeCode } from "anyagent/claude-code";

const agent = create(claudeCode());
const prompt =
  "Add the Acme SDK to this project: install the dependency, create " +
  "acme.config.ts with sensible defaults, and wire it into the app entry " +
  "point. Only edit files in this repo. Do not run git commit or git push.";

const result = await agent.run(prompt);
console.log(result.text);
```

`result.text` is the agent’s final answer; `events`, `usage`, `sessionId`, and `raw` carry the full event list, the token accounting, the resume handle, and the CLI’s untouched final payload. Holding a `RunResult` means the run succeeded, because every failure [throws instead](/docs/errors). For runs longer than a few seconds, show progress by [iterating the run](/docs/streaming) rather than waiting silently.

## Keep a run read-only

`readOnly: true` is the one restriction you can place on a run, and its contract is strict: nothing on the machine changes. No file writes, no shell commands. Use it for analysis and reporting features, where a retry or a wandering agent must stay side-effect free:

```ts
import { create, detect } from "anyagent";

const [found] = await detect();
if (!found) {
  throw new Error("No supported coding agent found.");
}

const agent = create(found);
if (agent.supports("readOnly")) {
  const report = await agent.run("Audit the error handling in src/api/.", {
    readOnly: true,
  });
  console.log(report.text);
}
```

Not every CLI can make that guarantee: goose, Cline, and Antigravity declare it unsupported, and requesting it throws [`UnsupportedCapability`](/docs/errors#unsupportedcapability) rather than pretending. The `supports` check above is both the runtime guard and what makes the option typecheck on a detected agent.

<Callout type="warn">
  There is no middle setting. A run without `readOnly` has the CLI’s full
  autonomy, file edits and shell included, with every approval prompt disabled.
  Scope the prompt, and point it at a directory you can restore. [How AnyAgent
  works](/docs/how-it-works#every-run-is-unattended) explains why no middle
  exists; harness-specific modes stay reachable via
  [`extraArgs`](/docs/escape-hatches).
</Callout>

## Tune the run

The remaining `RunOptions` fields shape one run:

```ts
import { create } from "anyagent";
import { claudeCode } from "anyagent/claude-code";

const agent = create(claudeCode());
await agent.run("Add input validation to the signup form.", {
  cwd: "/home/sam/projects/acme-app",
  model: "opus",
  effort: "high",
  systemPrompt: "Follow the Acme SDK conventions in docs/conventions.md.",
  env: { ACME_ENV: "development" },
});
```

- **`cwd`**: the directory the agent works in; defaults to the current process’s working directory
- **`model`**: a model name in the CLI’s own vocabulary, listed on each [adapter page](/docs/adapters) and by [`agent.models()`](#check-credentials-before-you-run) where the CLI can list them
- **`effort`**: how hard the model should think, from `"none"` to `"max"` and beyond; where a CLI’s vocabulary is closed, `capabilities.reasoningEfforts` lists the accepted values and anything else throws before the run starts
- **`systemPrompt`**: extra system-level instructions; on a CLI without a system-prompt flag AnyAgent folds them into the prompt as a preamble, where adherence is weaker
- **`attachments`**: file paths to attach to the prompt, passed on the CLI’s own attachment flag; gated, so guard it with `agent.supports("attachments")` where the agent is not known in advance
- **`env`**: extra environment variables, merged over the parent process’s environment

Every option is checked against the agent’s capabilities before any process spawns. When the agent is not known in advance, guard an option on `agent.capabilities`, and remember that model names are each CLI’s own vocabulary:

```ts
const wantsOpus = agent.adapter.meta.id === "claude-code";
const opts =
  wantsOpus && agent.capabilities.modelSelection ? { model: "opus" } : {};
await agent.run("Review the error handling in src/api/.", opts);
```

For `readOnly`, `effort`, `mcp`, `resume`, and `attachments`, guard with `agent.supports()` as shown in [Keep a run read-only](#keep-a-run-read-only): it answers the same question and narrows the agent’s type so the options compile.

## Resume a session

For a conversation spanning several runs, open a session: `agent.session()` threads the continuation for you, and [Run a conversation](/docs/sessions) covers it. The `resume` option underneath is there when you hold a session id from elsewhere: pass it and the run continues that conversation. The id is on a previous run’s `sessionId`, and streams surface it early as a [`session` event](/docs/api#agentevent):

```ts
import { create } from "anyagent";
import { claudeCode } from "anyagent/claude-code";

const agent = create(claudeCode());
const review = await agent.run("Review this repo for unhandled rejections.");

if (review.sessionId) {
  await agent.run("Fix the issues you found.", { resume: review.sessionId });
}
```

The `if` guard matters: `resume: undefined` starts a fresh session rather than throwing, and `sessionId` is absent on CLIs that never reveal one headless (goose and Cline today; each [adapter page](/docs/adapters) says which).

## Attach MCP servers

`mcp` attaches Model Context Protocol (MCP) servers for the run, keyed by the name the agent sees them under. Each entry sets `command`, `args`, and optional `env` for a local server, or `url` for a remote one:

```ts
import { create, detect } from "anyagent";

const [found] = await detect();
if (!found) {
  throw new Error("No supported coding agent found.");
}

const agent = create(found);
if (agent.supports("mcp")) {
  await agent.run("Describe the database schema this app expects.", {
    mcp: { db: { command: "npx", args: ["acme-db-mcp"] } },
  });
}
```

The option means exactly those servers: servers from the end user’s own configuration stay out of the run. On the CLIs that route MCP through their own config files instead, reach it through [escape hatches](/docs/escape-hatches); each [adapter page](/docs/adapters) says which route applies.

## Test without a CLI

`detect()` accepts a fake probe, so your tests simulate any machine without spawning a process. The probe is two functions: `which` resolves a binary name to a path or `undefined`, and `exec` returns a command’s output:

```ts
import { detect } from "anyagent";

const probe = {
  which: async (bin: string) =>
    bin === "claude" ? "/home/sam/.local/bin/claude" : undefined,
  exec: async () => ({ stdout: "2.0.31", stderr: "", code: 0 }),
};

const installed = await detect({ probe });
// One result: Claude Code 2.0.31, without touching PATH.
```

Pass `adapters` alongside `probe` to scan a subset or include a custom adapter; see [`DetectOptions`](/docs/api#detect). `create(found, { probe })` takes the richer [`SystemProbe`](/docs/api#systemprobe), which adds env, home-dir, and file reads, so tests can simulate credentials and drive `authStatus()` and `models()` with zero subprocesses.
