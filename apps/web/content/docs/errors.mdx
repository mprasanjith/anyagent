title: Handle errors
description: Branch on AnyAgentError.code to fail well in a tool you ship to other people.

Everything AnyAgent throws is one class, `AnyAgentError`, with no subclass tree. You branch on its `code`, one of four values, and turn each into a response that makes sense to your end user. Results never hide failures: holding a `RunResult` means the run succeeded, so a `try/catch` around the run is the whole story.

## Branch on the code

Import `AnyAgentError` and switch on `err.code`. There is nothing else to match against:

```ts
import { AnyAgentError } from "anyagent";

try {
  await agent.run(prompt);
} catch (err) {
  if (err instanceof AnyAgentError) {
    // branch on err.code
  }
  throw err;
}
```

## The four codes

Each code tells you where the run failed and what you can do about it in a shipped tool.

`UnsupportedCapability` fires when you ask for something the CLI cannot do: an option its capability table does not declare, or a permission level it does not offer. It is thrown before anything spawns. Fix your options, or read `agent.capabilities` first and degrade the feature when it is missing.

`Invocation` fires when the CLI itself went wrong: it failed to spawn, exited nonzero, or reported an agent-level error. Surface `stderr` to diagnose it. Common real causes are a missing binary, an expired login, and an installed CLI too old to know a flag you passed.

`Parse` fires when the CLI ran but its output did not match the shape the adapter expects, or the stream ended without a terminal `done` event. This points to a change in the CLI’s output format. Report it upstream so the adapter can be updated.

`Aborted` fires when your `AbortSignal` fired and the run was terminated. In a shipped tool that is the end user cancelling on purpose, so treat it as a normal exit rather than a failure.

## Diagnostic fields

Beyond `message` and `code`, three fields help you diagnose a failure and write useful bug reports:

- `raw`: the underlying cause, either a native error or the harness’s own error payload
- `argv`: the exact command line that ran, attached when a process was involved
- `stderr`: what the CLI printed to stderr, attached when a process was involved

Log all three when a run fails unexpectedly, so a bug report carries what ran and what the CLI said:

```ts
console.error(err.message);
console.error("command:", err.argv?.join(" "));
console.error("stderr:", err.stderr);
```

## A complete example

This wraps the `acme init` run and turns each code into a message for the end user:

```ts
import { AnyAgentError } from "anyagent";

try {
  const result = await agent.run(prompt, { permission: "edit" });
  console.log(result.text);
} catch (err) {
  if (!(err instanceof AnyAgentError)) {
    throw err;
  }
  switch (err.code) {
    case "Aborted":
      console.log("Cancelled.");
      process.exit(0);
    case "UnsupportedCapability":
      console.error(
        `${agent.adapter.meta.name} cannot do that: ${err.message}`
      );
      break;
    case "Invocation":
      console.error(
        "The agent failed to run. Check that it is installed and signed in."
      );
      console.error(err.stderr);
      break;
    case "Parse":
      console.error(
        "Unexpected output from the agent. Please report this to Acme."
      );
      console.error("command:", err.argv?.join(" "));
      break;
    default:
      throw err;
  }
  process.exit(1);
}
```

Each branch gives the end user something to act on.
