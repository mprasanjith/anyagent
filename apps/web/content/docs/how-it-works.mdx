AnyAgent runs a prompt by launching the coding-agent CLI installed on the machine and translating its output into normalized events. This page builds that mental model in five ideas: one surface across every agent, capability tables, detection that observes rather than chooses, one process per prompt, and a `raw` field that keeps every native detail reachable. Understand these and the rest of the API follows.

## One surface across every agent

The unified surface models the feature subset coding-agent CLIs have in common: a prompt goes in, a permission level bounds what the agent may touch, events stream out, and a final answer comes back. That shared subset is the whole surface. It never widens to fit one CLI.

This has a direct consequence for your code. Anything written against the surface runs on every supported agent unchanged. When you ask for something a CLI cannot do, the call throws `AnyAgentError` with `code: "UnsupportedCapability"` before any process spawns, so a wrong assumption fails at the call site rather than mid-run.

Each CLI still has native capabilities outside the surface, such as bidirectional sessions or finer permission flags. Those stay reachable through [escape hatches](/docs/escape-hatches) instead of widening the surface. Where a common feature is missing from one CLI’s flags, AnyAgent’s core can supply it uniformly rather than dropping it, which the next section calls emulation.

## Capability tables describe each agent

A `CapabilityTable` is the machine-readable answer to “what does this agent support”. Read it from `agent.capabilities` or any `DetectResult`, then adapt what you ask for:

```ts
const opts = agent.capabilities.modelSelection ? { model: "opus" } : {};
const result = await agent.run(prompt, opts);
```

This code sets `model` only when the agent supports choosing one, so the same call works across agents. Most fields guard the matching `RunOptions` field: requesting an option the table does not declare throws `UnsupportedCapability` before anything spawns. `streaming` is the one informational field, describing whether output arrives progressively rather than guarding an option, so `runStream` works either way. The table each CLI declares is on its [adapter page](/docs/adapters).

Every guarding field is one of three values, which the reference calls [`CapabilitySupport`](/docs/api#capabilitysupport):

- `"native"`: the CLI has its own flag, and the adapter maps your request onto it.
- `"emulated"`: the CLI has no such flag, so the core provides the behavior itself, identically on every agent that declares it. A system prompt folded into the prompt text on a CLI without an append-system flag is emulated; on Claude Code the same request is native.
- `false`: unavailable, and requesting it throws `UnsupportedCapability`.

Both `"native"` and `"emulated"` are truthy, so `capabilities.systemPrompt` reads the same way regardless of how the feature is provided:

```ts
const opts = agent.capabilities.systemPrompt
  ? { systemPrompt: "Follow the conventions in docs/conventions.md." }
  : {};
await agent.run(prompt, opts);
```

You ask for an emulated capability exactly as you ask for a native one, and the result is uniform across agents. Structured output and system prompts are both emulated on the CLIs whose flags lack them.

## Detection observes, never chooses

`detect()` checks the machine’s `PATH` for each supported CLI and returns one result per install, carrying the binary’s path, the reported version, and the agent’s capability table. The order of results carries no ranking, so picking an agent is your product decision; [Detect installed agents](/docs/detecting-agents) covers the patterns.

The version is for display only. AnyAgent targets current CLIs and never changes behavior based on the version it reads, and an agent whose version probe fails still works, with `version` set to `null`.

## One process per prompt

Every `run` or `runStream` call launches the agent’s CLI once, in its non-interactive mode, and the process exits when the agent finishes. There is no daemon and no state shared between calls: two runs are two independent processes.

The CLI runs exactly as the end user’s own terminal would run it, with their login, their configuration, and their subscription. That is why AnyAgent needs no API keys, and why a run bills the end user’s account rather than yours.

Conversation state lives with the CLI, so continuing a conversation across runs takes a session id passed as `resume`. Abandoning a run is safe too: when you break out of a `runStream` loop early, AnyAgent terminates the process for you.

## One event stream, native detail on raw

Whatever the CLI prints, you receive the same five event types: `text-delta`, `tool-call`, `tool-result`, `usage`, and a final `done` carrying the `RunResult`. How much text one `text-delta` carries varies by agent, from a token to a whole message, but concatenating every delta’s `text` always reproduces `RunResult.text` exactly.

Normalization drops CLI-specific detail from the fields your code branches on, and it keeps all of that detail reachable. Every event carries the CLI’s untouched native payload on its `raw` field, and `RunResult.raw` holds the final native payload: session ids, exact cache accounting, and anything the normalized fields leave out.

Session resume is the everyday case. A CLI reports its session id only in the raw payload, under its own key, so you read it there and pass it to the next run:

```ts
const first = await agent.run("Start reviewing this repo.");
const { session_id } = first.raw as { session_id?: string };

const followUp = await agent.run("Continue with src/.", { resume: session_id });
```

Each adapter page documents its raw shape, including the key its session id lives under.
