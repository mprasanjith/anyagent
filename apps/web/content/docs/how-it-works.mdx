title: How AnyAgent works
description: "The mental model behind AnyAgent: one process per prompt, capabilities you check before you ask, unattended runs, and native detail kept on raw."
---

AnyAgent runs a prompt by launching the coding-agent CLI installed on the machine and translating its output into normalized events. This page gives you the mental model in five parts: what a run is, how to know what an agent can do, why runs are unattended, how detection and sessions behave, and where the native detail lives.

## A run is one CLI process

Every `run` call launches the agent’s CLI once, in its non-interactive mode, and the process exits when the agent finishes. There is no daemon and no state shared between calls: two runs are two independent processes.

The CLI runs exactly as the end user’s own terminal would run it, with their login, their configuration, and their subscription. That is why AnyAgent needs no API keys, and why a run bills the end user’s account rather than yours.

## Check what an agent can do before you ask

Agents differ: `readOnly`, `effort`, `mcp`, and `resume` exist only on some CLIs. `agent.supports()` tells you before you ask, and inside a `true` branch the options also typecheck:

```ts
if (agent.supports("readOnly", "effort")) {
  await agent.run(prompt, { effort: "high", readOnly: true });
}
```

Requesting an option the agent does not support throws `AnyAgentError` with `code: "UnsupportedCapability"` before any process spawns, so a wrong assumption fails at the call site rather than mid-run. When you create an agent from a specific adapter, `create(claudeCode())`, the same mistake fails to compile.

Some options work on every agent even where the CLI has no flag for them, because AnyAgent provides the behavior itself: a `schema` produces a validated JSON reply everywhere, and a `systemPrompt` reaches every agent. You ask for these the same way regardless; where the provided form behaves differently from the CLI’s own, the docs for that option say so. The [support matrix](/docs/adapters) shows what every agent declares.

Two methods answer discovery questions rather than gate options: `agent.authStatus()` reports whether the CLI looks signed in, and `agent.models()` lists the models it accepts. Neither ever makes a paid model call, and on some CLIs the answer is a best-effort read of local credentials rather than the CLI’s own word; [Check credentials before you run](/docs/run-agents#check-credentials-before-you-run) covers how much to trust it.

## Every run is unattended

`run()` has no channel for answering an approval prompt: headless, nothing can say “yes” mid-run. So every run executes with the most autonomy its CLI offers, and there is no permission setting that waits for approval.

The one restriction is `readOnly: true`, with a strict contract: nothing on the machine changes. No file writes, no shell. An agent whose CLI cannot guarantee that declares `readOnly` unsupported and throws rather than approximating. Harness-specific modes between the two extremes stay reachable via [`extraArgs`](/docs/escape-hatches).

Because no one can intervene, the prompt carries the safety: [Run agents](/docs/run-agents#run-a-prompt-and-read-the-result) shows how to scope one.

## Detection observes, you choose

`detect()` checks the machine’s `PATH` for each supported CLI and returns one result per install, carrying the binary’s path, the reported version, and the agent’s capabilities. The order of results carries no ranking, so picking an agent is your product decision; [Run agents](/docs/run-agents) covers the patterns.

The version is for display only. AnyAgent targets current CLIs and never changes behavior based on the version it reads.

## One event stream, native detail on raw

Whatever the CLI prints, you receive the same event vocabulary: `session`, `text-delta`, `reasoning-delta`, `tool-call`, `tool-result`, `file-change`, `usage`, and a final `done` carrying the `RunResult`; [`AgentEvent`](/docs/api#agentevent) lists each one’s fields. Concatenating every delta’s `text` reproduces `RunResult.text` exactly.

Normalization never discards anything: every event carries the CLI’s untouched payload on its `raw` field, and tool events carry the CLI’s own tool name on `nativeName` beside the shared one on `name`.

Conversation state lives with the CLI, so a conversation across runs is a session id threaded between them. `agent.session()` does the threading for you:

```ts
const session = agent.session();
await session.run("Start reviewing this repo.");
await session.run("Continue with src/.");
```

Each turn is still one process; the session is client-side bookkeeping over the CLI’s own state. [Run a conversation](/docs/sessions) covers it, including persisting `session.id` to continue days later.
