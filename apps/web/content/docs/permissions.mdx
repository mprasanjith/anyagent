title: Permissions
description: The three autonomy levels, what each means for the user’s machine, and how AnyAgent maps them onto each CLI.

Every run carries one of three permission levels that bound how much the agent can do to the working directory: `read`, `edit` (the default), and `auto`. The enum never widens and never silently up- or downgrades your request.

## The three levels

Each level draws a different boundary around what the agent may touch:

- **`read`**: the agent inspects files and answers, but changes nothing
- **`edit`** (the default): the agent creates and modifies files, while the CLI’s own guardrails still gate riskier actions like shell commands
- **`auto`**: every prompt is auto-approved and the agent runs unattended

You set the level per run through `RunOptions.permission`:

```ts
await agent.run("Fix the failing test in test/parser.test.ts", {
  permission: "edit",
});
```

This run lets the agent edit files to fix the test, while its CLI still prompts before running commands you have not pre-approved. Omitting `permission` gives the same behavior, since `edit` is the default.

<Callout type="warn">
  `auto` disables the CLI’s own confirmation prompts, so the agent approves
  every action itself. Reserve it for sandboxed or disposable environments.
</Callout>

## Choosing a level for a shipped tool

Match the level to what your feature does:

- **Tools that change code**, a setup wizard or a codemod runner: `edit`. The agent writes files while the CLI’s guardrails still cover shell commands.
- **Features that inspect and report**, a repo analysis or a review summary: `read`, so the agent cannot alter the user’s project.
- **Sandboxed or disposable environments only**: `auto`, where auto-approving every action is safe.

## How the levels map onto CLIs

Native permission surfaces differ across harnesses: some CLIs take a three-way level flag, some a single autonomy switch, some a per-tool allowlist, and some grade autonomy finer than three levels. Each adapter translates your level onto whichever its CLI uses, and the mapping never lands on something stronger or weaker than you asked for. The exact flag behind each level is documented on the agent’s [adapter page](/docs/adapters).

AnyAgent always passes the level explicitly rather than relying on a CLI’s default, since a CLI whose own default is weaker or stronger than `edit` would otherwise silently change what runs.

## Why the enum stays fixed

Three levels are the whole surface, and AnyAgent never widens the enum for one harness. If a CLI cannot honor the level you ask for, the run throws `AnyAgentError` with `code: "UnsupportedCapability"` before any process spawns; check `agent.capabilities.permissionLevels` to see what an agent offers. A CLI with only a single autonomy switch, for example, cannot honor `read`.

Some CLIs have finer-grained native permission systems underneath, such as allow-listing individual tools. Those stay reachable through [escape hatches](/docs/escape-hatches), while the three-level enum remains the whole unified surface.
